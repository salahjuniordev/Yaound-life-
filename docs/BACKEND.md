# Backend

The game is offline-first. Supabase is optional and only used for cloud saves,
account upgrades, content reports and the shared city state. Without
`VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`, all of this is dead-code
eliminated from the client and the game uses local simulation only.

## Shared city state

`public.world_state` is one row per **server city day**. It carries:

- `fuel_price`
- `weather` (`sun`, `cloud`, `rain`)
- `strike` JSON (`{ "active": boolean }`)
- `delestage` JSON keyed by gameplay district, for example
  `{ "nlongkak": { "start": 600, "end": 720 } }`
- `events` JSON with `headlines` and `headlinesFr` arrays

The row is generated by
`public.generate_world_state(p_game_day integer default null)` in
`supabase/migrations/0002_world_state_cron.sql`. The generator is
deterministic for a given day, so a rerun refreshes the same row rather than
creating a new random state. `pg_cron` runs
`yaounde-world-state-daily` at **00:05 UTC** each day. The migration also creates
the current row immediately and can be backfilled manually:

```sql
select public.generate_world_state();
select public.generate_world_state(42); -- explicit server city day
```

The server day starts at `2026-01-01` and is **not** the player's local save
day. The client applies the latest published state without changing
`state.world.day`; each save keeps its own calendar.

### Client behaviour

- On game load/new game and on each local day rollover, the client fetches the
  latest row.
- It validates every field, clamps fuel to the gameplay range, ignores unknown
  districts and drops out-of-range outages.
- It applies weather, fuel, strike, outages and headlines, then saves the
  refreshed local snapshot.
- Offline, unconfigured or failed requests are no-ops. Local weather, fuel,
  strikes, outages and headlines continue to work as before.
- Older rows are ignored if a newer row was already applied in the same
  session.

### Permissions

- Clients may `SELECT` from `public.world_state`.
- Clients may not insert, update or delete rows.
- `generate_world_state(integer)` is revoked from `PUBLIC`, `anon` and
  `authenticated`; the migration owner, `service_role` and the cron scheduler
  can run it. The hosted project is verified this way.

### Verification

Apply the migration before expecting a live row:

```bash
npm run db:verify
```

The verifier checks that `world_state` is readable, that the latest row has the
expected shape when one exists, that clients cannot write it, that clients
cannot execute the generator, and then cleans up its probes. It prints skips
for the shape and generator checks when migration `0002` has not been applied.

## Migration order

1. `supabase/migrations/0001_init.sql`
2. `supabase/migrations/0002_world_state_cron.sql`

`pg_cron` must be available on the Postgres instance. On Supabase it is a
supported extension; the migration installs it only when it is not already
present, then creates/replaces the generator and schedule. Applying the
migration again is safe and refreshes the current row.

The hosted "mboa life" project has migration `0002` applied (2026-11-21):
`yaounde-world-state-daily` is active and `npm run db:verify` passes 17/17.
